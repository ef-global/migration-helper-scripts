# Interactive CLI Run Discovery Spec

## Goal

Make `migration-helper` easy to use for non-authors of the tool by adding a first-class interactive mode that understands `sb-mig` migration artifact sets automatically.

The user should not need to:

- remember the exact artifact file names
- manually pick `before` and `after` files for diffs
- manually type the migrations directory path for the common case

The tool should detect migration runs from `sbmig/migrations`, present them as choices, and then route the user into either `audit` or `diff`.

## Current State

Today:

- `migration-helper` with no args opens an interactive flow for `audit` only
- `diff` is only usable as a non-interactive command:
  - `migration-helper diff before.json after.json`
- the current audit prompt asks the user to manually type a file or directory path
- the tool does not understand `sb-mig` artifact groups as a single migration run concept

This is functional, but too low-level for day-to-day migration use by less technical operators.

## Product Direction

The default invocation:

```bash
migration-helper
```

should become a guided interactive CLI with two top-level modes:

- `audit`
- `diff`

The interactive mode must automatically discover migration runs in the migrations folder and let the user choose one of those runs rather than individual files.

Non-interactive mode must remain supported.

## Scope

In scope:

- add a top-level interactive entry flow for `migration-helper`
- discover `sb-mig` migration runs automatically from a migrations directory
- let the user choose between `audit` and `diff`
- let the user choose a discovered migration run instead of raw files
- keep existing path-based `audit` and `diff` automation intact
- support run names produced by custom `--fileName` values
- support timestamped and non-timestamped artifact file names

Out of scope for this phase:

- changing the validator contract
- changing the HTML diff renderer itself
- changing `sb-mig` artifact naming
- replacing existing non-interactive commands with prompts only
- supporting arbitrary JSON diff bundles that are not `sb-mig` runs

## Source Artifact Model

The interactive flow is based on the file artifacts generated by `sb-mig`.

From `sb-mig` behavior, a dry-run migration run can produce:

- `dry-run--<artifactBaseName>---<itemType>-input-full[__<timestamp>].json`
- `dry-run--<artifactBaseName>---<itemType>-after-full[__<timestamp>].json`
- `dry-run--<artifactBaseName>---<itemType>-to-migrate[__<timestamp>].json`
- `dry-run--<artifactBaseName>---<itemType>-migration-pipeline-summary[__<timestamp>].json`

Additional optional artifact:

- `dry-run--<artifactBaseName>---<itemType>-validation-failed[__<timestamp>].json`

Where:

- `artifactBaseName` is either:
  - the explicit `--fileName` value passed to `sb-mig`
  - or the generated fallback base name
- `itemType` is currently usually:
  - `story`
  - `preset`
- `timestamp` may or may not exist depending on how `sb-mig` was run

Examples:

- `dry-run--all---story-input-full.json`
- `dry-run--all---story-after-full.json`
- `dry-run--all---story-to-migrate.json`
- `dry-run--all---story-migration-pipeline-summary.json`

Or timestamped:

- `dry-run--my-run---story-input-full__2026-2-9_20-51.json`
- `dry-run--my-run---story-after-full__2026-2-9_20-51.json`

## Migration Run Definition

A migration run is a grouped set of artifact files that share:

- the same `artifactBaseName`
- the same `itemType`
- the same timestamp bucket, if present

The run entity should expose:

- `id`
- `artifactBaseName`
- `itemType`
- `timestamp`
- `directory`
- `artifactPrefix`
- `files.inputFull`
- `files.afterFull`
- `files.toMigrate`
- `files.pipelineSummary`
- `files.validationFailed`
- `isDryRun`
- `isComplete`
- `completeness.diffReady`
- `completeness.auditReady`
- `summary.totalItems`
- `summary.totalChangedItems`
- `summary.stepCount`
- `summary.validationIssueCount`

### Completeness rules

A run should be considered:

- `complete` for diff if both `inputFull` and `afterFull` exist
- `complete` for audit if at least one JSON artifact relevant for audit exists

Preferred audit target for a run:

- `toMigrate` if present
- otherwise `afterFull`
- otherwise `validationFailed`
- otherwise the run is not directly auditable from interactive mode

## Discovery Behavior

### Default directory discovery

When the user starts `migration-helper` interactively, the CLI should try these roots in order:

1. `MIGRATION_HELPER_RUNS_ROOT`, if set and valid
2. `./sbmig/migrations`
3. `./migration-previews`

If none exist, the CLI should ask for a directory path.

### File parsing

The run discovery layer should parse filenames using the real `sb-mig` shape, including:

- required `dry-run--` prefix for dry-run artifacts
- required `---` separator before `<itemType>-<artifactKind>`
- optional `__<timestamp>` suffix before `.json`

Proposed conceptual pattern:

```text
^dry-run--(?<artifactBaseName>.+)---(?<itemType>story|preset)-(?<artifactKind>input-full|after-full|to-migrate|migration-pipeline-summary|validation-failed)(?:__(?<timestamp>.+))?\.json$
```

The parser should be tolerant enough to support future item types, so `itemType` should not be hardcoded too tightly in implementation.

### Grouping rules

Runs should be grouped by:

- `artifactBaseName`
- `itemType`
- `timestamp || null`

This avoids collisions between:

- multiple runs that used the same `artifactBaseName` but different timestamps
- story and preset runs with the same base name

The `id` should be stable and human-readable, for example:

```text
story::all::no-ts
story::homepage-v4::2026-02-09_20-51
```

The internal grouping key should not depend on file ordering.

## Interactive UX

## Entry Flow

When the user runs:

```bash
migration-helper
```

the CLI should prompt:

1. `What do you want to do?`
   - `Audit migration run`
   - `Diff migration run`
   - `Change migrations directory`
   - `Exit`

Then it should discover migration runs and show selectable run options.

If no runs are found in the initial root:

- explain that no `sb-mig` runs were discovered
- ask for another directory
- allow exiting cleanly

## Run Selection UX

Each run choice should be human-readable and include enough metadata to disambiguate similar runs.

Suggested label shape:

```text
all · story · no timestamp · complete
brand-hub-v4 · story · 2026-02-09_20-51 · complete
homepage-preset-pass · preset · complete
```

Useful extra metadata for display if available from the summary file:

- changed item count
- step count
- validation issue total

Example richer label:

```text
all · story · changed 4/5 · 18 steps · complete
```

Suggested incomplete run label:

```text
homepage-pass · story · no timestamp · incomplete · missing after-full
```

## Diff Mode UX

After the user picks `Diff migration run` and then selects a run:

- the CLI should automatically use:
  - `inputFull` as the before file
  - `afterFull` as the after file

Then prompt:

1. `Serve diff locally?`
2. `Port?` if serving
3. `Output HTML file path?` with a default

Default output path could be:

- `./migration-diff-report.html`
- or a run-specific file like `./migration-diff-report--<run-id>.html`

If the selected run is incomplete for diff:

- the CLI should explain what is missing
- allow selecting another run

If the user chooses not to serve locally:

- the CLI should still print the final output HTML path
- the CLI should not require a port prompt

## Audit Mode UX

After the user picks `Audit migration run` and then selects a run:

- the CLI should auto-resolve the validators root
- the CLI should default the audit target to the run’s best audit artifact:
  - `toMigrate`
  - else `afterFull`
  - else `validationFailed`

Then prompt:

1. `Select validation scope`
   - `Full audit (all validators)`
   - one validator by name
2. `Audit artifact`
   - `Recommended: to-migrate`
   - `after-full`
   - `validation-failed`
2. `Output JSON?`
3. `Enable debug logs?`

The user should not be asked to type a file path in the happy path.

Advanced option may still be offered:

- `Choose another artifact from this run`

The default artifact selection logic should be:

1. `toMigrate`
2. `afterFull`
3. `validationFailed`

If a run has only `pipelineSummary` and no auditable content artifact, it should be listed as non-auditable.

## Non-Interactive Compatibility

These commands must continue to work unchanged:

- `migration-helper audit <file-or-dir> ...`
- `migration-helper diff <before.json> <after.json> ...`
- `migration-helper version`
- `migration-helper help`

Additional compatible enhancements are acceptable:

- `migration-helper diff` with no positional paths may fall back to interactive run selection
- `migration-helper audit` with no positional path may fall back to interactive run selection

But the explicit path-based workflows must remain stable for scripting and CI usage.

Additional ergonomic behavior is acceptable if it does not break current invocations:

- `migration-helper audit` with no path may open interactive audit mode
- `migration-helper diff` with no paths may open interactive diff mode
- `migration-helper diff <before> <after>` must continue to bypass prompts
- `migration-helper audit <target>` must continue to bypass prompts

## CLI Contract Changes

### `src/cli.ts`

Target behavior:

- `migration-helper`
  - launches top-level interactive menu
- `migration-helper audit`
  - interactive audit mode when no path is provided
- `migration-helper audit <file-or-dir> ...`
  - existing non-interactive audit behavior
- `migration-helper diff`
  - interactive diff mode when no file paths are provided
- `migration-helper diff <before> <after> ...`
  - existing non-interactive diff behavior

### `src/scripts/migration-audit-cli.ts`

This file currently mixes:

- help and version handling
- interactive audit prompts
- a special-case diff redirect

It should become either:

- a thin audit-specific interactive wrapper

or preferably:

- a narrower helper invoked by a new top-level interactive controller

The interactive controller should own mode selection. Audit-specific prompts should remain isolated from diff-specific prompts.

## Proposed Architecture

Add a dedicated run discovery module, separate from audit and diff logic.

Suggested new modules:

- `src/scripts/discover-migration-runs.ts`
- `src/scripts/interactive-run-selection.ts`

### `discover-migration-runs.ts`

Responsibilities:

- resolve candidate migrations roots
- scan JSON files
- parse filenames into artifact metadata
- group artifacts into runs
- optionally read pipeline summary files for extra display metadata

Suggested exported API:

- `findDefaultRunsRoot(): string | null`
- `discoverMigrationRuns({ root }): Promise<DiscoveredMigrationRun[]>`
- `parseMigrationArtifactFileName(fileName): ParsedMigrationArtifact | null`
- `selectBestAuditArtifact(run): string | null`

### `interactive-run-selection.ts`

Responsibilities:

- prompt for mode
- prompt for run selection
- route selected run into:
  - `runMigrationAudit(...)`
  - `runMigrationDiff(...)`

This keeps `src/cli.ts` thin and prevents `migration-audit-cli.ts` from becoming overloaded.

Suggested exported API:

- `runInteractiveMigrationHelper(args?): Promise<number>`
- `promptForRunsRoot(initialRoot?): Promise<string | null>`
- `promptForRunSelection(runs, mode): Promise<DiscoveredMigrationRun | null>`

## Summary File Enrichment

If a run contains `migration-pipeline-summary`, the discovery layer should read it and expose:

- `totalItems`
- `totalChangedItems`
- `steps.length`
- per-step validation issue counts

The discovery layer should treat summary parsing as best-effort:

- malformed summary JSON should not crash discovery
- failed summary parsing should only remove enrichment data for that run
- debug logs may mention the parsing failure

This is not required for correctness, but strongly improves the run selection UX.

## Edge Cases

The discovery layer must handle:

- multiple runs with the same base name but different timestamps
- incomplete runs where one or more files are missing
- directories containing unrelated JSON files
- both `story` and `preset` runs
- validation-failed artifacts without a full complete dry-run set
- large artifact directories
- timestamped and non-timestamped runs with the same base name in the same folder
- duplicate artifacts for the same logical slot

Expected behavior:

- unrelated JSON files should be ignored
- incomplete runs should still be listed, but clearly marked
- diff mode should only allow selection of runs with both `inputFull` and `afterFull`
- when duplicates exist for the same slot, the newest timestamped file or last lexicographic file should win consistently, and the rule should be documented in code comments

## Testing Plan

Add targeted tests for the new discovery and routing layer.

Recommended coverage:

- parse valid dry-run artifact names
- ignore unrelated JSON file names
- group four standard files into one run
- group timestamped files into separate runs from non-timestamped files
- distinguish `story` and `preset` runs with the same base name
- expose completeness flags correctly
- prefer `to-migrate` over `after-full` for audit target selection
- permit incomplete runs to display but reject them for diff
- preserve current `migration-helper diff before after` behavior
- preserve current `migration-helper audit target` behavior

Where practical, add light CLI routing tests around:

- `migration-helper`
- `migration-helper audit`
- `migration-helper diff`
- `migration-helper diff before after`

## Acceptance Criteria

The work is complete when:

- `migration-helper` with no args opens an interactive mode selector
- interactive mode discovers migration runs automatically from the migrations directory
- diff mode lets the user select a run and auto-wires before/after files
- audit mode lets the user select a run and auto-wires the best audit artifact
- run selection works for custom `--fileName` values and timestamped filenames
- current non-interactive `audit` and `diff` commands still work
- the CLI remains usable in apps where validators come from installed Backpack in `node_modules`
- a user can run the tool from a consuming app root and select a run from `sbmig/migrations` without typing raw file paths
- interactive mode works for both the default `all` run name and custom run names

## Suggested Implementation Order

1. Add filename parser and run grouping logic.
2. Add migrations root discovery for interactive mode.
3. Add interactive mode selector at top-level CLI.
4. Add interactive diff flow based on discovered runs.
5. Add interactive audit flow based on discovered runs.
6. Keep path-based non-interactive flows unchanged.
7. Add tests for run parsing and grouping.
8. Add tests for interactive command routing where practical.
9. Update README examples for the new interactive default behavior.

## Notes

- The current `migration-helper` already has interactive infrastructure through `inquirer`, so this work is an extension rather than a rewrite.
- The most important product change is conceptual: move from “pick files manually” to “pick a migration run”.
